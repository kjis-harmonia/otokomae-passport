## 検証順

1. ViteのStagingモードで、外部DBに接続しないローカル画面を確認する。画面端と主要ボタンを最優先に、小型端末と短い横向きから試す。
2. 同一ブラウザで幅・高さを順番に切り替える。iPhone・Android相当、小型折りたたみ・大画面、iPad相当、狭いPC・広いPCを分けて記録する。
3. 登録、QR、会員導線、予約、券、決済の入口と認証境界を確認する。DB操作の試験には隔離DBの合成データを使う。スタッフの認証後試験は方法を合意してから行う。
4. ガチャとPWAは、短い画面での操作、動画・通知・更新を分けて確認する。ネイティブのインストールや端末権限は実機の証跡がある場合だけ実機確認とする。
5. 再現できた不具合を修正し、同じ端末条件で確認する。最後にアプリ用型チェックと該当する回帰テストを実行する。

## 残存リスクと再開地点

### 予約の重なりとQR確認失敗（11月9日）

- 新規予約は、同じ人について選んだ施術時間が既存予約に重なる場合だけ画面で止める。開始と終了が接する枠は重なりとしない。担当が別でも、既存予約と重なる09:00には確定ボタンが出ず、重ならない08:00は新規確定し、09:00の元予約も残った。
- 銀ちゃんは新規・変更・取消の予約操作を、店頭QR確認が取れてから進める。確認RPCが503の間は仮押さえ・確定・取消の送信が0件。再確認しても自動送信せず、同じ人・時刻・メニュー、または同じ取消対象を表示してから確定ボタンを待つ。復旧後の新規と取消を390×844の画面とローカル実RPCで確認。別会員への切替では前会員の入力を送らない。
- 既存予約の入れ替えは変更手続きに任せる。別の時間帯の予約を追加した場合、以前の予約を取り消さない。
- QR確認失敗の再現は、ローカル試験サーバーを `access-down` にして確定ボタンを押し、送信0件を確認する。`normal` に戻して「もう一度確認」だけでは送信されず、同じ内容が表示されることを確認する。

#### DB保証の修正案（承認前）

使い捨てDBで、同じ本人の16:30を異なる担当者で2件確定できた。担当者・レーンの排他制約では施術対象者の重なりを検知しない。

1. 確定・変更・SB／取込の既存書き込みを棚卸しし、確実に照合できる施術対象者のキーを決める。お連れ様は登録済みの個人ID、本人は確定した顧客IDを使う。店舗や取込の行は顧客台帳の関連付けが確認できる場合に同じ本人キーへ解決する。氏名や電話番号だけで人物を推測しない。旧データで同行者の個人IDがない場合、本人に割り当てず件数と扱いを先に確認する。
2. 新規予約・変更の書き込みで、初回INSERTから正しい人のキーを設定する。現状、お連れ様のIDはINSERT後のUPDATEで付くため、単に本人の制約を追加すると、本人とお連れ様が同時に受ける正常な予約を弾く。変更では既存の原子的な取消・作成・引継ぎを維持する。
3. PostgreSQLで、人物キーが同じ有効予約の施術区間 `[starts_at, ends_at)` の重なりを拒否する。スタッフの準備時間の制約は別扱い。既存の重複・顧客IDの未照合・統合済みIDを読み取りで事前確認し、競合があれば適用前に止める。対象者を識別できない行はDB保証の対象外として明示する。
4. 同一人物・同時刻・別担当の並行送信は片方だけ成功、部分重複も拒否、隣接枠と別日、別のお連れ様、複数メニューは成功とする。変更で重複したときは元予約と付帯情報が残ることを回帰試験する。共有環境への適用は別承認。

対象は予約テーブルの制約と対象者IDを書き込む予約処理。ログイン、QR承認、本人確認のRPCはこの案に含めない。

4. **切替前に発行された遅延取消を区別する。** 2引数の取消も、単独取消と旧入れ替えの後半で同じ形になる。関連する予約が現在1件に見えることだけでは安全を証明できない。旧版からの取消が切替前に既に確定した入れ替えの続きである可能性を否定できない場合は、副作用の前に止め、新版で対象を確認して取り消すか店舗対応にする。取消の通常機能は新版の明示経路で維持する。旧版の2引数取消で安全と立証できるケースを残せるかは、切替履歴とRPC利用元を確認してから決める。安全を立証できない場合は旧入口で予約状態を変えない。既存データの予約を自動で取り消さない。
5. **切替順序を保証する。** 新版が使う安全なAPIを先に用意し、既存の処理を閉じる時点では予約の書き込みを一時停止して実行中の旧リクエストを確認する。単に待ち時間を設けて未実行とは扱わない。予約確定と取消の残存状態を照合し、ガードが有効になったあとに再開する。ガードを有効にしたまま画面の切り戻しが可能な手順を用意し、旧来の二段階入れ替えを再開しない。

実装後の合格条件は、開いたままの旧版で本人／お連れ様の入れ替えが予約確定前に止まること、旧仮押さえ・遅延取消・複数タブも同じこと、新版の通常新規・別日の追加・明示取消が従来の認可範囲で動くこと。旧新同時送信、確定応答消失、同一キーの再送・別内容での再送を、予約行・履歴・銀Pay残高と押さえ・割引券・ガチャ券・施術対象者まで照合する。店舗端末・SB・HQ・Hot Pepperの予約登録、受付と会計も回帰対象。SQL・RPC・製品コードには今回手を加えていない。

今回の使い捨てPG17では既存の予約変更安全性と人物重複防止のSQLスイートを再実行して合格。合成会員でDBコミット後にHTTP接続を落とし、別接続からの同一キー再送と結果照会が同じ完了結果を返した。さらに同じ元予約へ同一キー2送信と別キー1送信を同時に行い、同一キーの応答は一致し、変更は1回だけ成立した。本人の確定予約1件、お連れ様の予約と親への紐付け、銀Payの押さえ9,000円・残高12,000円・台帳増分0、割引券・ガチャ券の付け先を確認した。

Chromeで旧画面を開いたまま実際の新版Service Workerへ切り替え、旧画面のJavaScriptが残ることを確認した。新版を読み直しても同じ合成会員セッションを維持した。新版から原子的な変更を送信して確定後の応答を落とすと、画面は成功扱いにせず「結果を確認」を表示。通信復旧後の照会で成功が表示され、照会前後でDBの行は一致した。元予約は取消、新しい本人予約は2メニューを保持して1件のみ確定。旧版の二段階操作を拒否する新しいサーバーガードは承認前の設計で、この試験には含まれていない。

### ローカル実装

`supabase/migrations/20261109045326_customer_booking_cutover.sql` を追加。旧確定のRPC名と引数は維持し、既存予約と施術対象者の照合を確定のロック下で行う。旧2引数取消は、遅延した入れ替えの続きと区別できる情報がないため、対象が本人所有でも `booking_update_required` を返す。新版の単独取消は既存の本人所有・期限・ペナルティを使う別入口から行う。旧版の拒否時に確定・取消・券・残高は動かず、既に発行済みの仮押さえには従来の有効期限が適用される。

新版の追加確定は仮押さえIDと施術対象者を照合し、同じ依頼で保存済みの結果を返す。通信断後は端末に保存した同一依頼を再送する。従来の予約アシスタントの入れ替えは、対象の予約IDを銀ちゃんの変更画面へ渡す。変更先や料金は改めてサーバーの確認画面で確認する。複数人の入れ替えは、まず既存予約の変更へ案内する。以後の追加予約は別の操作として扱う。

公開時は、予約の書き込みを一時止め、実行中の旧RPCを確認してからDBと画面を切り替える。旧版の単独取消は新版を開き直すか店舗で行う。切替前に既に生じた重複予約は人が照合する。今回は使い捨てDBのみ。

ローカルChromeで旧画面を確認ボタンの手前に開いたままDBを切り替えた。旧版は `booking_update_required` を受け、予約行に変更がなく、取消RPCも呼ばなかった。同じセッションで新版を読み直して別時刻を明示追加し、確定応答と再送を一時遮断した。復旧後の「結果を確認」は同じ予約を表示し、確定後と結果表示後のDB行が一致した。予約変更、人物重複防止、店頭認証のSQL回帰、型チェック、ローカルビルド、差分チェックを確認した。
