その操作のあと、閉鎖Bの**直前**に次を再取得する。


履歴39・承認30人と照合値・予約設定・GINPay照合が期待どおりか確認。DB20完了時のdataとの差分があれば、その実機操作によるものと説明できるか確かめる。不明な変更を「テストのせい」として許容しない。③の01〜20の前後比較は従来どおり不変を要求する。

この読取をB直前の比較基準として保存してから、③末尾のpost_web_security_lockdown.sql→check_post_web_lockdown.sqlを1本ずつ人が実行する。B後は履歴40・security成功と、data/予約設定/承認がB直前の値から変わらないことを確認する。**この説明は比較のタイミングの明確化であり、DB SQL・履歴ガード・30人の条件を緩める変更ではない。**

閉鎖Bの直後、まだ営業を再開せず、以前の状態を残してある確認用PWA/ブラウザーで次を行う。

1. 古いセッションなしの入口から券・会員情報が読めなくなることを確認。真っ白、無限待機、知らない会員になるなどの問題があれば停止する。
2. アプリの削除やSafariのデータ消去をせず通常の再読み込み/開き直しで新画面へ進む。既存会員はFace IDログイン、未設定なら会員QR→店舗端末で本人確認→同じ会員のFace ID設定へ案内する。新規登録で代用しない。
3. 元と同じ会員ID・券・残高で続けられることを確認。旧画面が自動で引継ぎ案内を表示すると決めつけず、更新後の導線まで実機で確認する。失敗なら閉鎖Bの権限を開き直さず、営業再開を止める。

その後に⑦の全画面・実取引の確認を行う。本番テストは人が決めた会員・枚数・金額だけにし、Stagingの練習と混同しない。テスト記録を直接削除せず、必要な取消や照合は正式な操作で記録を残す。

## 戻せる範囲の境目

| 段階 | 復旧の考え方 |
|---|---|
| 本番変更前 | 作業中止。バックアップ原本を保持し、練習用コピーだけ削除 |
| DB適用を開始した後 | 失敗したSQLだけtransaction rollback。既に成功した工程は残り、全体が自動rollbackするわけではない |
| 05/06・旧書込閉鎖・15の後 | 旧店舗画面の発券や未確認客の予約に制限が出る。旧Webへ戻すだけでは営業再開できない |
| 関数の一部を更新した後 | 次の関数を出さず停止。旧version番号だけでは戻せず、その時のソースとDB互換性を確認してから個別に再デプロイする必要がある |
| Web公開後 | Vercelの画面だけのrollbackはDB/Supabase関数を戻さない。互換性が確認できたProduction deployment以外へ戻さない。Previewを旧本番として使わない |
| 閉鎖B成功後 | 旧読取の再開放は禁止。新しい認証導線を維持して修正する。公開前のmain（10/23時点 91c140f。当日09:00に記録したSHAを正とする）へ戻すだけの復旧手順は用意しない |
| 毎分cron開始後 | ⑤Hで停止。実行中/キュー中の要求・配達済み通知・作成済み仮押さえは取り消せない。状態を調べ、必要な正規操作を個別判断 |
| 新しい会計・発券・予約ができた後 | バックアップへの全復元で正しい新規データも失われ得る。即時復元はせず、差分を保全して人が復旧計画を決める |

Vercel Instant Rollbackは対象の制約があり、ビルド時の設定も元に戻る。rollback後にはProductionドメインの自動割当も止まるため、次のpushだけで公開が復旧したとは扱わない。使う場合は記録済みの対象・権限・DB互換性を確認したうえで、[公式手順](https://vercel.com/docs/instant-rollback)に従う。一般的な旧mainへのrollbackコマンドを、今回の安全な戻し方としては載せない。

## 中断時の作業票と終了

止めたら、時刻、固定release SHA、最後に成功した工程、エラーになった工程、履歴件数、関数version、ジョブactive、フラグの状態、意図した実機操作をGit外の作業票へ記録する。会員名・連絡先・トークン・cron本文・秘密をPRやチャットへ貼らない。

その場でSQLを作り直す、履歴を消す、人数を合わせる、権限を開き直す、同じ発行/会計を新しい番号でやり直すことはしない。最初のエラーで次へ進まず、営業再開の可否を人が判断する。保全した本番バックアップは残し、練習DBのコピーだけ削除する。バックアップの保存先はDesktop/otokomae-backups/日時/に限定する。

この⑥で実施したのは文書・確認器の作成だけ。本番・Staging・mainは変更せず、PR #11もDraftのまま。確認器は模擬git/npxで17ケース（別branch/dirty/古いHEAD/取得失敗/途中変更等の拒否、5関数の正常経路、失敗後の再試行なし）を検証。実デプロイ/ネットワーク0。実際のlatest/clean確認はこの変更をpushしてから読み取りだけで行う。⑦は作成済み。実機・スタッフ練習の完了報告と最終レビューは残る。
