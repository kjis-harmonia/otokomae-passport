# Staging → 本番の引っ越し手順（11/9〜）

方針：Staging をそのまま本番へ。**機能は増やさない、磨くだけ**。本番の操作はすべて慶一郎さんの承認のあと。

## 新しい流れのスイッチ

- `ginFlow()`（`src/utils/env.ts`）ひとつで切り替わる。Staging は常に入。本番は Vercel の環境変数 `VITE_GIN_FLOW=true` で入る。
- 中身：LINE 型の銀ちゃん（予約・変更・キャンセル・キャンセル待ち・店頭QRのあとの聞き取り）、☰「いつもの・お連れ様」、登録のあとはそのままホーム（最初の画面＝FirstGuide は出さない）。
- テスト用の道具（Staging の帯・リセット・ガチャ先行公開・登録なしで開く・`?firstguide`）は `isStaging()` のまま。本番には出ない。
- 新しい機能を Staging だけに出したいときも `isStaging()` ではなく `ginFlow()` を使う。

## 本番の下見の結果（11/9・読み取りのみ）

- 本番の migration 95本 ＝ main と同じ。2026100100xx の4本は記録を付ける前の土台なので流さない。流すのは上の10本だけ。
- 関数は空白・改行を無視して比べる（そのままだと改行の違いで全部ちがって見える）。違いは20個：17個は10本で書き直すもの、3つは無害（2つはコメントだけ、staff_security_check は本番が新しい→Staging を本番に合わせた）。**本番にだけある直しが消える危険はない。**
- 同じ人の重なりが本番に1組あった（慶一郎さんのテスト。メモが「お連れ様」だけの昔の形）→ 2本目の `res_is_companion` を「お連れ様で始まる」に広げて、本番データで0組を確認済み。
- 料金表は直す前の Staging と同じ → 10本目はそのまま効く。お客様ごとの料金がある人は2人（どちらも慶一郎さんのテスト）。
- 10本に出てくるメニューの記号は全部本番にある。

## 順番（引っ越しの日・お客様の少ない夜にまとめて）

1. **DB migration 1〜11 を本番へ**（1本ずつ、失敗したら止める。1本は「全部入る」か「何も変わらない」）。
2. **すぐに main へ PR → マージ → 公開**。★9本目を入れた瞬間から、今の本番アプリでは予約の取消・2件目の予約が断られる。1 と 2 の間は空けない。
   新しいアプリは `VITE_GIN_FLOW` が無くても新しい安全な入口を使うので、2 の時点で取消・予約は戻る（見た目は今のまま。登録画面のクリーム色だけ先に変わる）。
3. **Edge Function `johnny-agent` を本番へ deploy**（銀ちゃんの AI。無いと銀ちゃんの相談の返事が出ない）。
4. **Vercel 本番に `VITE_GIN_FLOW=true` → 公開し直し**。ここで銀ちゃんの会話・お連れ様・予約の変更に切り替わる。
5. **本番で確かめる**：テスト会員で予約 → 変更 → キャンセル、お連れ様、キャンセル待ち、店舗端末の〇名様受付・会計。

## 元に戻すとき（1本ずつ）

- 画面：Vercel の `VITE_GIN_FLOW` を外して公開し直す → 銀ちゃん以前の画面に戻る（予約・取消は新しい安全な入口のまま動く）。
- 9本目（旧版アプリの対策）：`supabase/rollback/20261109_cutover_restore.sql`（本番の11/9時点の関数そのもの）。古いアプリをまた使わせるときだけ。
- 10本目（料金）：`supabase/rollback/20261109_prices_restore.sql`。
- 11本目（変更で担当を選ぶ）：`supabase/rollback/20261110_change_staff_off.sql`（7・8本目の時点の reservation_review・reservation_mutate に戻す。11/10 Staging で中身を確認）。
- 8本目（重なり防止）：`supabase/rollback/20261108_overlap_off.sql`（制約だけ外す。データは変えない）。
- 1〜7本目：足すだけの変更（新しい表・列・関数）なので戻さない。古い画面は新しい列を使わないだけ。
- 予約・券・銀Payの記録は、どの戻し方でも消さない。
